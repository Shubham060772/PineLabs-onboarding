## Verification API demonstration without a paid provider

The supplied plan (§2 and §3, requirements C3 and C5) calls for at least two simulated verification services and asynchronous callbacks. Real provider integrations are explicitly excluded. The application implements PAN, GST, BANK and RISK through a separate provider simulator with actual HTTP requests and signed callbacks.

For a demonstration with the current database, start with `start.cmd`. Sign in as a merchant, create an application with **Fill synthetic sample**, and save the draft. This creates matching structured evidence; use the public PDF samples instead when demonstrating actual extraction. Do not mix values from different samples.

1. In another tab, sign in as an operator. Open **Provider simulator**, select the draft application and configure the desired response before submission. Use a short callback delay (such as two seconds) for the normal case.
2. Submit the draft as the merchant. Show **Fields & documents** for extraction and deterministic validation, then **Checks** for the verification API flow, request references, provider acknowledgement references and callback timestamps.
3. The backend sends `POST /mock/pan/verify`, `/mock/gst/verify` and `/mock/bank/verify`. Each accepted request returns HTTP 202 with a provider request ID. The provider later sends a signed callback to `/api/v1/webhooks/providers/:provider`. RISK runs after the other three checks pass.
4. Show the transition from waiting for a callback to passed, then approval and simulated merchant-ID provisioning. Use **Timeline** to show recorded transitions.
5. On a new draft, configure GST to **FAIL** before submission. Show the failed check and blocked approval. A timeout/503 scenario demonstrates retries; a duplicate-callback scenario demonstrates one applied result despite repeated deliveries.

The default simulator response is success unless a scenario overrides it. It does not query a government or bank registry. Present this as: “We perform extraction and validation, then call simulated verification APIs through the same asynchronous workflow used for an external provider.” A synthetic identifier passing this flow is a demonstration result, not evidence of a real registration. No paid API credentials are needed.

Status interpretation is shared by the merchant and operator detail pages. A check is **cleared** only when its current provider result passes and its associated document has no outstanding validation/review issue. For example, four successful API responses with an unresolved GST name mismatch show **3 of 4 checks cleared**, GST **In Review**, and a separate **Provider API (simulated): Passed** result. Resolving the exception updates the document, field, validation-finding and check displays together. The original finding remains recorded, and the application stays **In Review** until the operator approves it. A later submission requires its own review; a prior resolution does not silently clear new findings. Timeline and attempt records remain historical evidence.

## Seeded presentation

Rejection is terminal: outstanding exceptions close with resolution `APPLICATION_REJECTED`, and open information requests are cancelled. For **INVALID_DOCUMENTS**, the operator selects the documents causing rejection and records a note; those documents and their combined checks display **Invalid**. Outstanding document reviews display **Rejected** with their recorded issue; other unfinished work displays **Cancelled**. Successful API results remain visible as historical results. The rejection reason and note are shown to merchant and operator. Migration 002 closes leftover open exceptions on already rejected applications and infers invalid documents only where the saved rejection reason and validation findings support it.
